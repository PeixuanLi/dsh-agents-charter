# 评审权威是公布的公式

[English](weighted-review.md) | 中文

- 所属层：[L1 — 角色分权](../layers/l1-role-separation.zh.md)
- 管辖范围：评审权威是公布的公式——指定 owner 加实测的代码所有权加贡献历史——而不是资历或声量。

## 规则正文

本机制没有常驻规则文本：公式与其策略代码住在源仓库的评审配置里，可移植的材料就是公布的公式本身。合并需要 2 分。每名指定 owner 贡献 2 分；write 权限的评审贡献 1 分，并按改动行的 git blame 归属加权为 `min(2, 1 + 4×ownedLines/totalLines)`——占改动区 25% 已到上限。作者按 `min(100, merged PRs) × 11/1000` 积累信用分，封顶 1.1，人与 agent（智能体）同规则，且永远不够单独达标。write 权限评审的 `CHANGES_REQUESTED` 是硬阻断，与总分无关。

## 执法

一个必需检查在每个 PR（Pull Request）上按公式重算每位评审者的权重，只在达到阈值时允许合并；`CHANGES_REQUESTED` 阻断独立于分数生效。`Ported-config reference: reference/github/review-ownership/ and reference/github/weighted-approval*.yml`（里程碑 M3 恢复）。

## 成本与前提

配置加等待时间：workflow 需要评审权重管道，而所有权与信用两项要在数月共享历史之后才有分量——刚初始化的仓库没有可测量的东西。低于中型且成员稳定的水位时，指定评审人要求能用更低成本提供同样的保护。

## 档位建议

Solo ✗ · Small ✗ · Medium ✓ · Large ✓ —— 公式读的是历史与成员稳定性；对小型或不稳定成员的团队，分数没有分量，仪式是空的。

## 移植清单

- 指定 owner 名单，与公式一起公布分值，让评审权威在被行使之前就可计算。
- 在贡献量还在增长时采用公式，而不是事后补建：所有权与信用两项需要积累的历史才有意义。
- 按 git blame 归属为 write 评审加权，并给作者信用分封顶，让多产的作者永远无法单独合并自己的变更。
- 把 write 权限评审的 `CHANGES_REQUESTED` 做成独立于总分的硬阻断。
- 公式对人类与 agent 作者一视同仁；豁免任何一方的规则都不是计量化的信任。

## 失效模式

没有公式的权威会固化成资历或声量：嗓门最大或资历最老的评审者成为闸门，没有人说得出依据什么规则；有了公式，评审权重追踪的是真实所有权。
