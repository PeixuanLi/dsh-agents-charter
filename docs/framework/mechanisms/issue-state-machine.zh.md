# issue 状态由事件推动

[English](issue-state-machine.md) | 中文

- 所属层：[L5 — 流程自动化](../layers/l5-process-automation.zh.md)
- 管辖范围：issue 状态更新由具体事件驱动，而不是人工整理。

## 规则正文

本机制没有常驻规则文本；它的源就是事件驱动的 workflow 本身。监听器订阅平台的原生类型事件（`typed`、`untyped`）与看板字段事件（`field_added`、`field_removed`），并据此移动工作项。策略代码从默认分支检出执行，分支保护让它可信；事件数据只是输入——构造出来的事件无法夹带策略。

## 执法

workflow 就是执法：状态变更只在事件触发时发生，人工维护的状态因此会以可见的方式偏离事件产出的状态。移植配置参照：`issue-lifecycle.yml` 与 `issue-policy.yml` 两个 workflow，恢复于 [reference/github/](../../../reference/github/README.md) 之下。

## 成本与前提

需要一个活的流程来驱动：只有 issue 流量稳定到人工整理成为瓶颈时，这套机器才养得起自己。前提是受保护的默认分支——让检出的策略代码可信的信任边界——以及读事件所写状态的消费方，比如看板与路由。

## 档位建议

Solo ✗ · Small ✓ · Medium ✓ · Large ✓ —— 它需要一个活的流程来驱动；solo 的 issue 流量太低，机器养不活自己。

## 移植清单

- 把每个状态迁移写成监听应触发它的事件——原生类型事件管分类变化，看板字段事件管看板移动。
- 策略代码在运行时从默认分支检出；事件载荷只作数据消费，永不作指令消费。
- 先保护默认分支；不受保护的策略代码会倒转信任边界。
- 用驱动事件来验证：开一个测试 issue，触发每个迁移，确认状态在没有人工编辑的情况下移动了。

## 失效模式

没有事件推动状态，看板就衰减成没人相信的陈旧标签：状态在有人想起来的时候才变，分拣状态偏离现实，看板不再是证据。衰减足够缓慢，每一次手工编辑都显得无害——这正是整理习惯重新形成的方式。
